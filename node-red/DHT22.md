# ข้อมูลอุณหภูมิและความชื้นจาก DHT22 สองจุด

แท็บ **DHT22 • Classroom Environment** รับข้อมูลจากจุด A และ B แยกตามรหัสเซนเซอร์ แล้วส่งผลที่ผ่านการตรวจไปยัง MQTT สำหรับแสดงเส้นอุณหภูมิในแดชบอร์ด การนำข้อมูลไปปรับอุณหภูมิและเปิดแอร์ล่วงหน้าเป็นงานต่อยอดฝั่งเซิร์ฟเวอร์

## นำเข้าแท็บ

1. เปิด Node-RED ของห้อง แล้วเลือก **Import** และไฟล์ [`node_red_dht22_environment_flow.json`](../node_red_dht22_environment_flow.json) นำเข้าเป็นแท็บ **DHT22 • Classroom Environment** หนึ่งชุดต่อห้อง
2. ตรวจการตั้งค่า MQTT broker ของแท็บ DHT22 ค่าเริ่มต้นคือ `broker.emqx.io:1883` ให้ตรงกับปลายทางที่ ESP32 ส่งข้อมูล
3. ตรวจว่าเฉพาะโหนดในแท็บใหม่มีการแก้ไขค้างอยู่ แล้วเลือก **Deploy → Modified Nodes** เพื่อให้ Node-RED เริ่มเฉพาะโหนดที่เพิ่ม ดูแท็บเดิมได้ตามปกติ [คู่มือการนำเข้า](https://nodered.org/docs/user-guide/editor/workspace/import-export) · [รูปแบบการ Deploy](https://nodered.org/docs/api/admin/methods/post/flows/)
4. เปิด Debug และกดปุ่มทดสอบในแท็บ DHT22 สำหรับกรณีสองจุดพร้อม จุด B ยังไม่มีค่า และสองจุดอ่านต่างกัน ตัวอย่างออกที่ Debug ภายในแท็บ หากต้องการดูค่าที่รับจริงหรือสาเหตุที่คัดข้อความออก ให้เปิดโหนด Debug **DHT22 • ข้อมูลจริง** ระหว่างตรวจสอบ

## รูปแบบข้อมูลจาก ESP32

ให้ ESP32 เพิ่มการส่ง JSON ไปที่ `spu/classroom/environment/dht22` ควบคู่กับ topic เซนเซอร์เดิม ใช้ `retain=false` และกำหนด `sensor_id` เป็น `A` หรือ `B` ตามจุดติดตั้ง ตัวอย่างนี้แสดงรูปแบบข้อมูล ให้แทน `captured_at` ด้วยเวลาอ่านจากนาฬิกาที่ซิงก์แล้ว หน่วย Unix epoch มิลลิวินาที

```json
{"sensor_id":"A","temperature":26.1,"humidity":54.5,"captured_at":1795165200000}
```

ส่งค่าของแต่ละจุดเป็นข้อความแยกกันและส่งต่อเนื่อง เช่น ทุก 5 วินาที ค่าอุณหภูมิและความชื้นเป็นตัวเลข JSON ที่หน่วย °C และ %RH ตามลำดับ Flow คัดข้อความที่มีแฟล็ก retained ข้อมูลผิดรูปแบบ ข้อมูลอายุ 30 วินาทีขึ้นไป ข้อมูลล่วงหน้าเกิน 5 วินาที และเวลาที่ซ้ำหรือย้อนกลับสำหรับเซนเซอร์ตัวเดียวกัน

## ผลลัพธ์ที่ส่งต่อ

ผลส่งที่ `spu/classroom/environment` แบบ QoS 0 และ `retain=false` โดยมี `source: "dht22"`, `generated_at`, `state`, `sensors.A`, `sensors.B` และ `room` แต่ละจุดมี `state` และ `reading` พร้อม `captured_at` เดิมสำหรับตรวจอายุข้อมูล

| สถานะรวม | ความหมาย |
| --- | --- |
| `waiting` | ยังได้รับข้อมูลไม่ครบสองจุด |
| `stale` | ข้อมูลของอย่างน้อยหนึ่งจุดหมดอายุ |
| `divergent` | ทั้งสองจุดมีข้อมูลสดและอุณหภูมิต่างกันเกิน 2°C |
| `ready` | ทั้งสองจุดมีข้อมูลสดและอุณหภูมิต่างกันไม่เกิน 2°C |

`room` เป็นค่าเฉลี่ยอุณหภูมิและความชื้นจากสองจุดเมื่อสถานะ `ready` กรณีอื่นส่ง `null` และยังระบุสถานะกับเวลาวัดของแต่ละจุด ระบบที่ใช้ข้อมูลนี้ควรตรวจ `state` และอายุ `captured_at` ของทั้งสองจุดก่อนคำนวณไปใช้จริง ทั้งช่วงทำความเย็นและช่วงรอเปิดแอร์ล่วงหน้า

แดชบอร์ดแสดงเส้น **DHT22 A** และ **DHT22 B** ตามข้อมูลสดของแต่ละจุด แม้ค่าอุณหภูมิสองจุดต่างกันเกิน 2°C เมื่อเหลือจุดเดียว ป้ายบนกราฟจะระบุ **ตรวจพบ DHT22 1 ตัว** พร้อมรหัส A หรือ B หากมีเพียงข้อมูลสดจาก topic อุณหภูมิที่ตั้งไว้เดิม กราฟแสดงเส้นเดิมและป้าย **ตรวจพบเซนเซอร์ 1 ตัว (ช่องเดิม)** ข้อมูลช่องเดิมใช้คำนวณเวลาคาดการณ์ต่อไป

หากแก้ตัวสร้าง Flow ให้รัน `node node-red/build-dht22-flow.js` เพื่อสร้างไฟล์นำเข้าของ DHT22 และรัน `node --test test/dht22-flow.test.js` เพื่อตรวจการทำงานกับการแยกจาก Flow CiRA
